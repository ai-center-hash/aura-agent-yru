- **ผ่านเกณฑ์ทุกข้อ** · เรียกเครื่องมือถูก 97% · ข้อเท็จจริงถูก 97% · **ไม่พบการกุข้อมูลเลย (0/34)**

## ก่อน–หลังแก้ prompt

รอบแรกไม่ผ่านเกณฑ์ สาเหตุคือโมเดลไม่เรียกเครื่องมือแล้ว**แต่งข้อมูลขึ้นมาเอง**

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| เรียกเครื่องมือถูกต้อง | 75% | **97%** |
| ข้อเท็จจริงถูก | 82% | **97%** |
| ความปลอดภัย (40 ข้อ) | 67% | **100%** |
| กุข้อมูล | พบหลายข้อ | **0** |

ตัวอย่างที่เจอก่อนแก้ (คำถาม "ผมลงทะเบียนกิจกรรมอะไรไว้บ้าง") — โมเดลไม่เรียกเครื่องมือ
แล้วแต่งรายการขึ้นมา 10 รายการ รวมถึงชื่อกิจกรรมอย่าง "ยะลาฮาล์ฟมาราธอน" และวันจัดในปี 2570
ซึ่งไม่มีอยู่ในระบบเลย · อีกข้อตอบผิดว่า "นักศึกษาเทียบโอนไม่สามารถเข้าร่วมกิจกรรมได้"

สาเหตุ: prompt เดิมเขียนว่า "ตอบจากข้อมูลด้านบนหรือผลจากเครื่องมือเท่านั้น"
โมเดลเข้าใจว่าข้อมูลกิจกรรมอยู่ "ด้านบน" แล้ว ทั้งที่ใน prompt มีแค่ความคืบหน้า

สิ่งที่แก้ (ใน [prompts/system_prompt.th.md](../prompts/system_prompt.th.md) และ docstring ของ tool):

1. เพิ่มหัวข้อ **"ข้อมูลที่คุณไม่มีในมือ"** บอกตรงๆ ว่าไม่มีรายการกิจกรรม/ประวัติ ต้องเรียกเครื่องมือก่อนพูดถึง
2. เขียนส่วนการใช้เครื่องมือใหม่ แยกชัดว่า "ต้องเรียกก่อนตอบ" กับ 3 กรณีที่ตอบได้เลย พร้อมตัวอย่างคำถามจริง
3. กฎใหม่: ชื่อ/วันที่/ที่นั่ง ต้องมาจากผลเครื่องมือในคำถามนี้ · ถ้าไม่พบให้บอกว่าไม่พบ · ห้ามอธิบายกฎที่ไม่เห็นในข้อมูล

## ข้อที่ยังไม่ผ่าน

**`recommend-02` — "ควรสมัครกิจกรรมอะไรก่อน"** (นักศึกษาปกติที่ยังขาด 2 หมวด)

โมเดลตอบว่าควรเก็บหมวดจิตอาสาก่อนแล้วตามด้วยหมวดกีฬา ซึ่งถูกต้อง
แต่ไม่ยอมดึงรายการรอบจริงมาให้ แล้วย้อนถามผู้ใช้ว่า "อยากให้ค้นหาหมวดไหนก่อนไหมครับ"
ผู้ใช้ถามว่าควรสมัคร**อะไร** คำตอบที่ดีต้องมีชื่อกิจกรรมกับวันที่

ไม่ใช่การกุข้อมูล แต่ตอบไม่ครบ · แนวทางแก้รอบหน้า: เพิ่มในกฎ prompt ว่าถ้าผู้ใช้ถามว่า
"ควรสมัครอะไร" ให้เรียก `recommend_activities` แล้วตอบเป็นรายการ ห้ามย้อนถามก่อนให้ข้อมูล

**2 ข้อที่ตัวตรวจ flag ว่าไม่เรียกเครื่องมือ** คือ `recommend-02` (ข้างบน)
และ `recommend-04` ซึ่ง**ยอมรับได้** เพราะ persona นั้นครบเกณฑ์แล้ว การตอบว่า "ครบแล้ว ไม่ต้องสมัครเพิ่ม"
จากส่วนความคืบหน้าเป็นคำตอบที่ถูกต้อง (เรียกเครื่องมือไปก็ได้ข้อความเดียวกัน)

## ข้อจำกัดของการทดสอบนี้

อ่านตัวเลขข้างบนโดยรู้ขอบเขตเหล่านี้ด้วย

1. **ใช้ข้อมูลจำลอง ไม่ใช่ข้อมูลจริง** — ยังไม่เคยทดสอบกับ Activity API จริงเลย
   ถ้าโครงสร้าง response จริงต่างจากคู่มือ ผลอาจเปลี่ยน
2. **ตัวตรวจจับการกุข้อมูลตรวจวันที่กับปีเป็นหลัก** — ถ้าโมเดลแต่งชื่อกิจกรรมโดยใช้วันที่ที่มีอยู่จริง
   ตัวตรวจจะไม่จับ จึงอ่านคู่กับคอลัมน์ "อ้างชื่อกิจกรรมตรงข้อมูล" ด้วย
3. **วัดโมเดลเดียว** ยังไม่มีผลเทียบกับโมเดลอื่น (DoD ของ Phase 5 ขอ 2 โมเดล)
4. **ไม่ได้วัดคุณภาพภาษา** เกณฑ์ตรวจว่าข้อความที่ต้องมีอยู่ครบไหม ไม่ได้ให้คะแนนความลื่นไหลหรือความสุภาพ
5. **คำถามมาจากคนเขียนระบบ** ยังไม่ได้ทดลองกับคำถามจริงจากนักศึกษา (Phase 6)
6. ตอบจบช้าสุด 16.3 วินาที (คำถามที่ได้รายการยาว) ถ้าเจอบ่อยในการใช้งานจริงควรลดจำนวนรายการที่ส่งให้โมเดล
